# ADR 0009: MVCC version placement and snapshot isolation

- Status: accepted
- Date: 2026-10-03
- Phase: 3

## Context

Phase 2 left two engines that both implement last-writer-wins. A reader sees the snapshot from `Begin`, and a later commit of the same key replaces the earlier one. Phase 3 needs snapshot isolation, first-committer-wins, and garbage collection of old versions, on both engines.

[ADR 0007](0007-disk-engine.md) makes a disk commit durable by logging full page images between `TxnBegin` and `TxnCommit`, syncing, and only then publishing those pages. A logical write-set payload in `TxnCommit` would not replay onto a tree whose pages were only partly published. Page and WAL format versions stay 1.

Open question 2 asked whether versions live inline in the primary key or in the `V` keyspace.

## Decision

**Versions are a head record in the key's own keyspace, plus history in `KSVersion` (`V`).** `internal/txn` sits on `storage.Engine`. `graphstore` stays unversioned and runs on a `storage.Tx`. The manager implements `storage.Engine`, so `graph.Graph` can sit on it. The memory engine and the disk engine are unchanged: last writer still wins on a raw engine.

The head value is magic `0xA5`, `createTS` and `deleteTS` as big-endian uint64, then the payload. `deleteTS` 0 means the version is live. A value without the magic is a pre-manager payload (`createTS` 0, always visible) until `Open` wraps it.

Chain records live in `KSVersion`. The key is `0x01`, the keyspace byte, the key length as uint32, the key, and `createTS`. The value is `deleteTS` plus the payload. The oracle is key `0x00` in the same keyspace: format byte `1`, the next transaction id, and the last commit timestamp. A format byte newer than 1 is `InvalidArgument` and the database is not used. `Open` migrates raw values in place, in one inner commit, wrapping each as a head with `createTS` 1.

A read at snapshot `S` sees a committed version when `createTS ≤ S` and (`deleteTS` is 0 or `deleteTS > S`). Uncommitted writes never reach the store. A transaction sees its own write set first. `Get` and cursors share `Visible`.

**Commit is one underlying storage transaction.** The order is:

1. `BeforeCommit`. An error leaves the transaction open and writes nothing.
2. Validate the write set. A key whose head was created or deleted after this snapshot is `Conflict` and retryable. The transaction stays open so the caller can roll it back. `InsertUnique` that loses the key, or that finds a live key, is `ConstraintViolation` and is not retryable.
3. Assign `commitTS + 1`. The oracle is not published until the inner commit succeeds.
4. Write the new heads, archive the previous heads into `KSVersion`, and write the oracle.
5. Commit the inner transaction. On the disk engine that is the page-image protocol from [ADR 0007](0007-disk-engine.md): `TxnBegin`, page images, `TxnCommit` with an empty payload, `wal.Sync`, then publish. A crash before that `TxnCommit` installs nothing. A crash after it installs the whole write set.
6. Publish the in-memory commit timestamp and drop the transaction from the open set.
7. `AfterCommit`. An error means the commit already happened.

A read-only commit and an empty commit publish nothing and skip the hooks. `Rollback` discards the write set. If it had writes, and the engine implements `AbortLogger`, the disk engine appends `TxnAbort` and syncs. Recovery already drops a transaction that never logged `TxnCommit`. The abort record is an explicit marker, not a second copy of the write set.

**No row lock is held across statements.** Writers do not wait for other writers. The only lock taken for the whole validate-and-apply step is the manager's commit lock, and it is not held while the transaction runs. Two transactions cannot deadlock waiting for each other's keys. A disk cursor still holds its tree read lock until `Close`; that is a storage-engine lock, not an MVCC lock, and it is the rule in [ADR 0007](0007-disk-engine.md).

`VACUUM` deletes chain records and dead heads whose `deleteTS` is at or before the oldest open snapshot (or the commit timestamp when nothing is open). Dead heads are not live keys. A background worker runs only when `GCInterval` is set. The shell leaves it at zero.

Limits default to 1024 open transactions and 100000 keys in one write set. A negative value disables that cap. `IdleTimeout` of zero disables the idle check. Past a limit, the error is `ResourceExhausted`.

## Alternatives considered

1. **Inline every historical version in the primary key** (`key` plus `createTS`). A range scan of live records would walk dead versions. The head stays the latest value, so a point read and a live scan do not read history unless the snapshot is older than the head.
2. **History only, no head.** Every read would seek the newest visible chain record. The head makes the common case one `Get`.
3. **Put the write set in the `TxnCommit` payload and apply it after the log sync.** That is what the phase plan sketched. Replaying a logical write set onto the disk tree conflicts with page-image redo. One MVCC commit mapped onto one storage commit keeps the crash boundary the page engine already has: nothing, or the whole write set.
4. **Pessimistic row locks, including `SELECT … FOR UPDATE`.** That can deadlock, and write skew would then be rejected. Snapshot isolation allows write skew. Locking a row across statements is backlog.

## Consequences

- Readers of a key do not take a lock that a writer of other keys must wait for. A commit still takes the underlying engine's commit lock for the duration of that one storage transaction.
- Page and WAL format versions stay 1. The MVCC stamp is the oracle byte in `KSVersion`.
- `graph.New` stays on the raw memory engine, so existing graph tests keep last-writer-wins. The shell opens the memory engine through the manager.
- Transaction ids and commit timestamps are different counters. The next transaction id is stored when a commit lands, so a crash can reuse an id that never committed. A commit timestamp is stored in the same storage commit as the data, so it is not reused.
- Write skew is allowed. Two transactions can each read two keys and each update a different one.

## Follow-up

- `SELECT … FOR UPDATE`, or any lock that rejects write skew, is backlog.
- Prometheus export of `versions_reclaimed_total` and `oldest_snapshot_age_seconds` is Phase 8. The counters are `MVCCStats` until then.
- Index builds in Phase 5 must version index records the same way, or run inside one of these transactions.
